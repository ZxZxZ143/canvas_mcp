# Security design

These are architecture-wide requirements. Phase 1/2 and the [Phase 3 secure file layer](../secure-file-layer.md) implement the relevant credential, network, mapping, pagination and Windows download/storage controls. MCP and isolated inspection remain future work. [ADR-006](decisions/ADR-006-secure-file-layer.md) established the initial download and internal path contract; [ADR-007](decisions/ADR-007-same-origin-download-auth.md) covered the historical browser-route behavior; [ADR-008](decisions/ADR-008-public-url-primary-download.md) defines the current production capability strategy. The local MVP trusts the operator's OS account and reviewed code/configuration; it cannot defend against arbitrary same-account process inspection.

## Trust and privilege boundaries

| Surface | Trust | Required treatment |
| --- | --- | --- |
| System instructions, operator-controlled AGENTS/skills, reviewed local code | Trusted policy | Canvas content cannot replace or modify it |
| Operator configuration | Trusted only after validation | Origins, roots and limits are never tool arguments |
| MCP arguments and continuation tokens | Untrusted ingress, even from a legitimate user | Central schema validation; then independent object authorization |
| Canvas JSON, instructor text, HTML, titles, filenames and links | Untrusted external data | Strict response mapping and bounded inert text; no execution authority |
| PDF/Office/code/notebook/archive bytes | Untrusted external data | Controlled download followed by separate constrained inspection |

Canvas is authoritative only about coursework facts. It is not an authority to reveal secrets, change policy, run commands, upload local files, or contact a link. A rubric may ask for code as a deliverable; that does not automatically authorize executing supplied code. Host/agent policy must preserve this distinction. Text wrapping, HTML stripping and MCP annotations alone do not solve prompt injection. Explicit user intent and normal tool authorization still govern actions.

The server's query allowlist and absence of command handlers enforce the Canvas read boundary. The initial Canvas client only uses fixed GET routes; neither a generic HTTP tool nor a “method” argument is exposed. MCP `readOnlyHint` is descriptive, not authorization. Downloading is read-only with respect to Canvas but creates a bounded local artifact. Future writes require a separate command interface and registration, capability checks, current object authorization, immutable action/payload digest, explicit user confirmation with expiry, and an audit record. Read credentials must never silently acquire command capabilities. Approvals are not inferred from course content.

## Credentials, identity, and process isolation

Only the outer credential adapter reads `CANVAS_ACCESS_TOKEN`. It resolves the secret for an authorized connection and supplies it to the Canvas API client for that connection's exact origin. Domain/application/MCP query DTOs contain no token. The token must never enter logs, errors, telemetry, tool results, file metadata, downloaded files or document parsers. `AccessToken(repr=False)` does not protect `asdict`, exception formatting or memory: no generic object serialization is permitted across these boundaries.

The launch arrangement matters: supply the token only to the server process environment, not the parent Codex/inspector environment or a command-line argument. Do not launch parsers as unreviewed children of the credential-bearing server. Any inspector has an explicitly constructed environment without server secrets, receives only an authorized file capability and resource limits, has network disabled, and can read only its staged artifact. No server environment, home directory or credential-store access is granted. Strong process separation requires OS sandboxing or a separate identity where available; clearing environment variables alone is not a sandbox. The local same-account limitation remains explicit. The architecture does not claim that an arbitrary existing reader is safe merely because its name is a PDF tool.

API and download clients are distinct. Under ADR-007 the download client obtains a scoped token for the initial fixed Canvas request and keeps it only while redirects stay on the exact configured Canvas origin. An external hop permanently ends Authorization, including on a return to Canvas. Redirect requests have no cookies, proxy credentials, netrc or ambient authentication. Environment proxy configuration is not used. Explicitly approved proxies need their own egress review. OAuth refresh and inbound MCP authentication remain separate future boundaries.

Every operation has server-created principal and connection scope. A connection binds origin/provider and the verified authenticated Canvas user ID (not just the institution's Canvas account ID). No student/user/token/connection selector is accepted in MVP tools. Use the authenticated subject for submission and grade queries; reject unauthorized parent/child pairings even when IDs are valid. Future remote connections require ownership authorization on every request. Subject/origin changes revoke cursors/artifacts and create a new binding; same-subject token rotation still rechecks access. Read permission may change during a session.

## Input, output, and error handling

The application ingress contract owns tool argument schemas; transports expose those rules without reinventing them. Canvas IDs are canonical ASCII positive decimal strings, 1–20 digits and <= 2^63-1, no leading zero, whitespace, sign, separators, percent syntax or URL. The provider reuses this same codec for values entering its route builder; encode route segments once, never concatenate raw input or decode twice. Other providers define their own codec. Dates, page bounds and sizes follow [tool contracts](mcp-tools.md).

This is not “validate only once everywhere”: hostile upstream JSON, authorization, network destinations, and filesystem operations are separate boundaries with their own checks. Dataclasses and NewTypes in this scaffold are declarations only. They provide no runtime validation or isolation.

Output serializers project an allowlist of fields. No raw Canvas payload, URL, signed query string, token, arbitrary error text or path leaks by generic serialization. External text is bounded and marked untrusted; control characters/terminal escapes and active HTML are removed or rendered inert. Build inert text and bounded material references separately: extract supported first-party assignment/file IDs, authorize metadata, then strip markup. Unknown, malformed, cross-course, inaccessible, external-tool and arbitrary web references remain unfetched and classified. Do not treat a URL inside HTML as a download capability. Unresolved relevant references make the context explicitly incomplete.

Phase 3 permits a generated absolute path in the internal local `DownloadedFile`; future MCP projection must be reviewed separately. This local-only handoff permits no general filesystem paths. Tool errors use fixed safe messages and request IDs. Catch-all errors never expose stack traces or `str(exception)`. Optional debug logs cannot override these rules.

## Outbound request policy

The Canvas base setting is an exact HTTPS origin on port 443 (DNS hostname or public IP literal), with no username/password, fragment, query, or path. No discovery, web scraping, arbitrary web fetch, or base-URL tool argument exists. Global DNS answers are allowed dynamically. For this local personal MVP only, `CANVAS_TRUSTED_PRIVATE_IPS` permits exact RFC1918/ULA destinations for the configured Canvas hostname; any untrusted DNS answer rejects the whole resolution. The deprecated `CANVAS_ALLOW_PRIVATE_ORIGIN=true` fails without that exact list. Private IP-literal origins and loopback, link-local, unspecified, multicast, reserved, metadata, mapped IPv6 and alternative encoded-IP spellings remain rejected. External capability origins and redirect chains never inherit private trust. Validation and the actual connection use the same vetted address set and original host for TLS SNI/certificate checks to prevent DNS rebinding. A future hosted multi-user plugin needs administrator-approved institution configuration, verified tenant setup or a private network connector instead of a user-controlled flag. Require egress/TLS tests for the selected HTTP client rather than claiming a hostname check is sufficient.

API routes are fixed, method GET, exact origin, and same expected resource family. Reject API redirects and pagination links that change origin/path scope or introduce unexpected parameters. Do not forward authorization through API redirects. Schema-valid IDs do not permit changing the configured institution.

Downloads start only from newly authorized Canvas file metadata. Metadata URLs are ignored; the initial fixed Canvas download route is constructed from verified IDs. The bearer token remains present while redirects stay on the exact configured Canvas origin. A redirect to an approved external origin permanently ends authorization, even if the chain returns to Canvas; it also switches to the separate public-only DNS pool. Signed redirect URLs remain infrastructure-private. Accepted origins are configured Canvas plus exact operator-reviewed HTTPS CDN origins, never wildcard/learned hosts. Validate every redirect hop, pinned DNS/TLS, maximum three redirects, no downgrade/userinfo/unapproved private destinations. See ADR-007 and the file guide for tested details.

Timeout and byte budgets cover streams, not just Content-Length. Request `identity` encoding, disable automatic HTTP decompression and reject unexpected Content-Encoding. Limits apply even when declared size is absent/false. API bodies also have a size cap; compressed API bodies are either rejected or decoded under a separate bounded decoded-byte counter. No hidden automatic decompression may bypass limits.

## Filesystem and format policy

An absolute root outside the project is selected by the operator and validated lazily before the first download. Owner/SYSTEM-only permissions, fresh session directories and random `.part`/`.blob` basenames are mandatory. Remote filenames are display-only untrusted text, never interpreted as paths. This excludes traversal, drive/UNC paths, ADS, device names and remote-name collisions by construction. Only the Windows concrete implementation is currently supported.

Creation and reopen must be race-resistant: exclusive creation, no following links/reparse points, confinement beneath an already verified root/handle, and verification of the opened object's identity. A pre-open `resolve()` or string-prefix check is insufficient. POSIX and Windows junction/reparse semantics require separate implementations and tests. If the platform cannot establish confinement, reject downloads. Do not implement a weaker fallback to meet portability claims. Private directory ownership mitigates other-user races but not a compromised same-OS-user process.

Reserve per-session disk/file quota before streaming, enforce actual bytes, discard partials on any failure, and publish an immutable artifact record only after completion. Finalization never overwrites another object. A digest identifies completed content; recheck registry, expiry, binding and opened-file identity before inspection. Root deletion/replacement fails closed. Normal cleanup only targets registered artifacts under the verified root; crash recovery uses the narrower owned-session rule below. No recursive deletion based on a remote name or user-provided path. Cleanup errors produce safe operator notices, not deletion outside scope.

Windows crash recovery is implemented using a small exclusive session marker: version, random session ID, owner SID, creation and expiry, never credentials/URLs/course content. At first storage use, an exclusive delete-on-close root lease proves no live store owns the root. Bounded recovery validates ownership/ACLs, marker, generated names, regular single-link file identities and total bytes before deletion by handle; only the empty verified session directory is then removed. Unknown/invalid entries remain untouched and block new storage. Old access capabilities are never recovered. This is temporary lifecycle metadata, not a general cache/index. Capability expiry is checked on access; physical cleanup is lazy, explicit or on session close, with no daemon.

| Content | Download policy | Inspection policy |
| --- | --- | --- |
| PDF | Bounded data; no automatic open | Isolated parser, no scripts/actions/network |
| DOCX/PPTX/XLSX | Allowlisted Office container candidates, inert storage | Isolated container-aware reader; member count/expanded bytes/ratio/depth limits; macros/external relationships disabled |
| CSV/TXT/JSON/source/notebook/dataset text | Bounded inert data; strict text handling | Never evaluate notebook cells, formulas, shell scripts or source code |
| ZIP/other archive | Opaque download only within byte limit | No automatic extraction; unsupported as a coursework inspection format initially |
| HTML/SVG/active content, executables, macro-enabled Office, unknown binary | Reject by default | No renderer or execution |

Content-Length, MIME and extension are claims, not facts. Storage performs bounded signature/type checks without a general document parser. A generic `application/octet-stream` is acceptable only if the independently observed type is allowlisted; otherwise reject. Inconsistent specific MIME/extension/signature means reject. Office files require a ZIP signature and bounded central-directory/member-name evidence for the declared OOXML type; active members are rejected before publication. This is still a container check, not a claim that OOXML is safe. Deeper semantic and polyglot checks belong to an isolated inspector before use. Unsupported legacy Office/spreadsheet formats are an explicit limitation, not a reason to execute a converter in the server. Type checks cannot guarantee that a PDF or Office document is harmless.

## Local artifact handoff and separate inspection

The implemented `FileDownloads` port returns `DownloadedFile` with an internal generated path, ID, provenance, type evidence, byte count, SHA-256 and expiry. `resolve_download` rechecks registry/scope/expiry, connection binding, upstream object permission, file identity/hash and confinement. `cleanup_download` accepts only scoped generated IDs. The earlier `CourseArtifacts`/`LocalArtifactResolver` declarations remain unimplemented architecture sketches. There is no MCP tool result or generic file-read tool; future local/remote handoff requires separate transport review.

The trusted host uses that result only to stage/read the approved bytes in its credential-free inspector. Allowed operation is read/inspect; no execution, extraction, mutation or ambient project access follows from the grant. A raw path alone is not an enforceable sandbox capability; the host must restrict the reader and revalidate content identity at handoff. The server cannot enforce safety of an unrestricted external host after bytes leave its control. Local artifact access expires after 24 hours or session end; later requests fail, and expiry cannot erase copies the host already made. A restarted server invalidates all old handles. Disconnect cleanup applies to server-managed artifacts only.

Host compatibility and constrained inspection are release gates: demonstrate that the target Codex host can receive this path and pass only the artifact to an appropriately isolated reader. If it cannot, report file inspection as unsupported and do not silently open an arbitrary reader. The architecture supports this workflow; this scaffold does not implement or certify the host bridge. A remote transport must not expose local paths and must replace the local bridge with authenticated, scope-bound resource streaming with equivalent quotas/expiry; no remote endpoint or resource tool is created now.

## Continuations and privacy

MVP cursors are cryptographically random references to bounded process-memory state, not Base64-encoded URLs. They bind principal, connection/binding version, operation, canonical query/filters/course scope, expiry and contract version. Unknown, modified, expired, cross-scope or mismatched cursors are validation errors with no existence details. Recheck authorization and give each resume a fresh bounded request ledger; each session also has a cursor-count/TTL cap. Retain only minimal validated traversal positions/IDs and query bindings, never raw payloads, full DTO pages, descriptions, signed URLs or unbounded deduplication buffers. A cursor retains at most 4 KiB and all cursors at most 256 KiB per session, including any transitively referenced adapter traversal state. Exceeding either byte ceiling produces explicit incomplete coverage and requires a narrower query; do not hide retained data in another unaccounted map. Resetting a per-request budget does not permit an unbounded single request. State is destroyed on session end/rebinding. A future stateless cursor needs authenticated integrity/encryption as appropriate and equivalent binding. Results are live views, not transactional snapshots; deduplicate by scoped entity ID within bounded scans and report observation times.

| Data | Location and lifecycle |
| --- | --- |
| Runtime DTOs/raw payloads | Memory for request only; discard after response; raw payloads never debug-logged |
| Pagination state | Memory only, 10-minute TTL, maximum 64 entries, 4 KiB/entry and 256 KiB/session, invalidated on restart/rebinding |
| Temporary downloads | Owner-only scoped root plus minimal lifecycle marker; partials removed promptly, 24-hour TTL/session-end cleanup, verified owned-session crash recovery as specified above |
| Cache | Disabled (`CACHE_TTL=0`); enabling requires an explicit adapter/isolation/retention design |
| Persistent application data | Optional private local MIME reports/scoped aliases under the [diagnostic contract](../mime-diagnostic-and-learning.md); no coursework database or background synchronization |
| Secrets | Server-only env initially; no artifact/cache/log copy; Python cannot guarantee zeroization |
| Logs | Allowlisted stderr; no disk log rotation by the app; the host owns retention and should disable unnecessary capture |

Logs contain operation code, correlation ID, counts, elapsed duration and safe category; no titles, filenames, search text, URLs, authorization headers, payloads, parser output or upstream exception text. Debug mode may add timings, counters and fixed allowlisted rejection subcategories, never underlying metadata values. Telemetry is off. Future audits use pseudonymous scoped identities, event/outcome codes and retention controls, never coursework content or secrets. Ordinary Python memory, OS crash dumps and host transcripts are residual operator-environment risks, not reasons to claim secrecy beyond the process boundary.
